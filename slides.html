Block 1 · 20 minutes

Propose
and Approve.

Schema proposals as the API contract.
Block 1 · Why this matters for NAB
First subgraph live. Now scale federation well.

Three things get hard as more subgraphs come online:

  1. A breaking change in one subgraph can break another subgraph's clients
  2. Reviewers need to know what is changing and who is affected
  3. Governance has to live inside the tooling, not in a Confluence page
07
Block 1 · Mental model
A schema is a contract.
Publishing a schema change is either
honoring that contract, or breaking it.

Every API carries breaking-change risk; monolith or federated graph, the contract is the contract. The difference is what catches the breaks. Most monolithic APIs find out at runtime, in production.

Apollo GraphOS gives federated graphs the tools to catch breaks before the merge button: schema proposals, composition checks, and operation-impact analysis against real traffic.

08
Block 1 · The mental model
A proposal is like a PR; it doesn't change anything on its own.

Once approved, the owning team still implements the change. The proposal flips to Implemented when the matching schema is published.

  1. Author opens a proposal in Studio
  2. GraphOS analyzes: composition, breaking changes, operation impact
  3. Reviewers approve, reject, or comment
  4. Owning team implements the change in their subgraph repo
  5. When the matching schema is published, GraphOS marks the proposal Implemented
09
Block 1 · What GraphOS analyzes
Four checks, automatic, every proposal.
CompositionDoes this still produce a valid supergraph?
Breaking changesAre types/fields removed, renamed, or made stricter?
Operation impactWhich client queries from real traffic would break?
Federation impactWhich subgraphs are affected via @key, @requires, @provides?

Without proposals, you discover all four in production. With proposals, you discover them before the merge button.

10
Block 1 · The proposal we'll walk together
Add a Cart subgraph.

The existing graph has products, users, reviews. Today's proposal adds a Cart entity, a CartItem value type, and a User.carts field:

type Cart @key(fields: "id") {
  id: ID!
  total: Float!
  totalQuantity: Int!
  products: [CartItem!]!
  user: User!
}

type CartItem {
  quantity: Int!
  product: Product!
}

type User @key(fields: "id") {
  id: ID!
  carts: [Cart!]!
}

type Product @key(fields: "id", resolvable: false) {
  id: ID!
}
11
Block 1 · GraphOS report
"Affected Operations: 0" is the punchline.
Composition Status: OK
Breaking Changes: 0 (additive: new entity, new value type, new field on User)
Affected Operations: 0
Federation Impact: users subgraph gains a new resolver dependency;
  cart references Product via CartItem.product (resolved by products subgraph)
Recommendation: Safe to implement.

Three Fed 2 patterns visible in one proposal: a new entity with @key, cross-subgraph field contribution via matching @key on User, and a stub declaration Product @key(..., resolvable: false).

12
Block 1 · Schema checks
Three ways a check fails. All caught before merge.

Every proposal (and every CI rover subgraph check) runs these:

  1. Composition — the supergraph doesn't compose. Conflicting key fields, missing types, federation directive misuse.
  2. Operation check — a field this proposal removes or changes is used by real client traffic. GraphOS shows which operations and which client versions.
  3. Lint — schema design rule violations: naming, nullability, deprecation patterns, NAB conventions you encode.

Live demo from Studio: one of each, on the workshop graph.

13
Block 1 · How this lands at NAB
Three places proposals plug into NAB's flow.
  1. BFF consolidation reviews. As BFFs collapse into federated subgraphs, proposals are the structured place to evaluate each merge.
  2. Cross-team field ownership disputes. @override migrations are exactly the kind of change you want a proposal flow on.
  3. The audit trail for compliance. Every proposal has a timeline: who proposed, who approved, when implemented. That's a compliance artifact, not just a workflow.

Block 2 · The story
Approved. Now what?

The owning team will implement the Cart subgraph for real. That takes days.

Meanwhile, every downstream team wants something queryable today.

The pattern
Spin up a standalone mock server that serves the proposal's API schema with auto-generated fake data. Hand the URL to client teams. They develop against it as if the backend were live.
16
Block 2 · Architecture
Two services, running in parallel.
Production-now
Router + products + users + reviews
Real DummyJSON data · :4000
Proposal-preview
mock-server (standalone)
@graphql-tools/mock · :4003

Clients pick based on what they need. Real data → router (4000). Proposal preview → mock (4003).

Mock server is not a federation subgraph. It's a parallel artifact representing a future API state.

Block 2 · Tour the code
Three things to read first.
  1. subgraphs/products/ and subgraphs/users/: TypeScript subgraphs using buildSubgraphSchema, backed by DummyJSON. Both expose entities with @key(fields: "id") and __resolveReference.
  2. mock-server/src/index.ts: pre-built. Uses makeExecutableSchema + addMocksToSchema. Plain GraphQL, not a subgraph.

19
Block 2 · Fill in the mock schema
Fetch the proposal variant directly.

Behind the scenes, every proposal is its own variant. pnpm dev:mock always fetches the latest schema for the variant you give it, then starts the mock server.

pnpm dev:mock p-0       # whichever variant the Cart proposal is on

The proposal's API schema (current API + Cart additions) lands in mock-server/schema.graphql and the mock server boots on port 4003. Nodemon watches for further edits and hot-reloads.

No variant arg defaults to @dev. Override with prod, p-1, etc.

20
Block 2 · Under the hood
Zero resolver code. Full mock data.
const typeDefs = gql(readFileSync('./schema.graphql', 'utf8'));
const schema = makeExecutableSchema({ typeDefs });
const mockedSchema = addMocksToSchema({ schema });

const server = new ApolloServer({ schema: mockedSchema });

addMocksToSchema walks every type in the schema and auto-generates fake values: strings become "Hello World", floats become random numbers, IDs become unique strings. No resolvers required.

What we're NOT doing: no buildSubgraphSchema, no federation directives, no _service field. Plain GraphQL.

Block 2 · Why this matters at NAB
The parallel-development primitive.

Every time the team approves a schema change, you hand client teams a mocked API for the future state while the backend catches up.

In production you'd host the mock server somewhere durable (a static URL, a Fly.io app, whatever fits NAB's infrastructure) and version it alongside the proposal. When the proposal moves to Implemented, decommission the mock and clients point at the router.

Block 3 · Build the Cart subgraph
We're going to build it.

A brand new federated subgraph at subgraphs/cart/. Four steps:

  1. Create the schema from the approved proposal's types
  2. Wire up resolvers (AI does most of the typing via the apollo-server skill)
  3. Register it in router/supergraph.yaml and run it on port 4005
  4. Publish to GraphOS and watch the proposal flip to Implemented

Cart isn't in the supergraph yet. By the end of Block 3, it is.

Block 3 · AI writes the subgraph
Tell AI what to build.

The workshop ships a ready-made build prompt at workshop/CART_PROMPT.md. Open it, copy the prompt block, and paste it into Cursor or Claude Code from the workshop root.

Slash command + brief
/apollo-server ... build a new subgraph at subgraphs/cart/, port 4005, schema + DummyJSON endpoints + resolver list spelled out below. AI writes package.json, tsconfig, src/index.ts, schema.graphql, and the federation resolvers.

Review the output before accepting. Then from the workshop root:

pnpm install      # picks up the new workspace package
pnpm dev:cart     # starts the cart subgraph on port 4005

If anything goes off the rails, git checkout block-3-completed has a known-good version.

Bonus · Apollo Connectors
The same Cart, as pure schema.
extend schema
  @link(url: "https://specs.apollo.dev/connect/v0.2", import: ["@source", "@connect"])
  @source(name: "dummyjson", http: { baseURL: "https://dummyjson.com" })

type Cart @key(fields: "id") {
  id: ID!
  total: Float!
  user: User!
}

type Query {
  cart(id: ID!): Cart
    @connect(
      source: "dummyjson"
      http: { GET: "/carts/{$args.id}" }
      selection: "id total user: { id: $.userId }"
    )
}

No Node project, no resolver code. The router executes the HTTP requests; selection transforms the REST response into GraphQL fields.

32
Bonus · When to reach for Connectors
For NAB: a natural fit for BFF consolidation.

Connectors fits when

  • The subgraph mostly wraps a REST API with light shaping
  • Most NAB systems-of-record subgraphs would qualify
  • You want schema-as-transformation, not code-as-transformation

Hand-written still fits when

  • Custom business logic in resolvers
  • Complex authentication flows
  • Transformations the selection mapping can't express
